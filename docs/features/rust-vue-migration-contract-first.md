# Rust + Vue Migration with Contract-First API Sync

## Status

Completed (2026-05-23)

## Summary

Migrate from SvelteKit + Node server runtime to a split architecture with a Rust backend API and a Vue frontend, using OpenAPI as the single contract source to keep both sides synchronized.

## Problem Statement

Current implementation couples frontend and backend in SvelteKit/Node. The product needs a backend stack with stronger systems-level safety and simpler operational characteristics, while keeping frontend development lightweight. Without strict contract controls, API/frontend drift risk increases during migration.

## User Story

As a self-hosted file manager operator and contributor, I want the backend in Rust and frontend in Vue with automated API contract synchronization, so that file operations remain secure and predictable while development stays maintainable.

## Scope

- In scope: scaffold a Rust API service for file operations (list, download, rename, move, delete)
- In scope: scaffold a Vue frontend that consumes generated API clients
- In scope: define OpenAPI generation from Rust types/handlers as canonical contract output
- In scope: add CI checks that fail on contract drift between backend and frontend client artifacts
- In scope: preserve existing path security guarantees (normalization, traversal blocking, symlink escape prevention)
- In scope: provide migration docs and validation workflow

## Non-Goals

- Not in scope: immediate removal of existing SvelteKit code during initial scaffold
- Not in scope: authentication/authorization redesign
- Not in scope: adding non-file-manager domains
- Not in scope: introducing multiple API versions in initial migration step

## UX / Flow

1. Contributor updates Rust endpoint or DTO.
2. OpenAPI spec is regenerated from backend source.
3. Vue API client/types are regenerated from the OpenAPI spec.
4. CI verifies generated artifacts are committed and in sync.
5. If drift exists, CI fails with explicit contract sync errors.
6. User-facing flows continue to use stable, typed API interactions.

## Technical Notes

- Add a new Rust backend workspace under `backend/`.
- Add OpenAPI output under `api/openapi.yaml` generated by backend tooling.
- Add Vue app under `frontend/`.
- Generate frontend API client into `frontend/src/lib/api/generated/` from `api/openapi.yaml`.
- Add scripts for contract generation and verification at repository root.
- Preserve current security invariants from existing server path guards and file service logic.

## Security Considerations

- Backend remains authoritative for path validation and file access rules.
- Reject traversal, absolute path abuse, and symlink escape in Rust implementation.
- Keep error responses explicit but non-sensitive.
- Treat OpenAPI as public contract; do not include internal-sensitive fields.
- Ensure generated client reflects server-side validation/error shapes to reduce unsafe frontend assumptions.

## Acceptance Criteria

- [x] Rust backend scaffold exists with OpenAPI generation enabled.
- [x] Canonical OpenAPI artifact is committed and reproducible.
- [x] Vue frontend scaffold exists with generated API client wiring.
- [x] CI fails if OpenAPI spec or generated frontend client is out of date.
- [x] At least one backend contract test validates response shape/status.
- [x] At least one frontend integration test verifies generated client flow against backend.
- [x] Migration docs describe phased cutover and validation gates.

## Test Plan

- Unit: Rust path normalization, traversal blocking, and symlink boundary checks (`backend/src/lib.rs` unit tests plus the `backend/tests/symlink_escape.rs` regression test).
- Integration: backend endpoint contract tests against OpenAPI-described structures.
- End-to-end/manual: Vue flow invoking generated client against running backend.
- CI quality gates: contract generation check, lint, frontend build, frontend typecheck (vue-tsc --noEmit over frontend/src and tests/), backend and integration tests, the frontend is TypeScript.

## Open Questions

- Should frontend client generation happen from committed `api/openapi.yaml` or direct backend runtime endpoint in CI?
- Should initial migration keep all endpoints under `/api/v1` to simplify future versioning?
